# خطة مقترحة — خدمة «سداد باقات ستارلينك»

## 1. السياق والدوافع

- وكيل ستارلينك الرسمي في اليمن رفض التعاون ولا يتيح السداد إلا عبر البنوك — احتكار وأسعار مرتفعة وأحجام باقات مقيدة (عالمياً البيانات غير محدودة).
- الهدف: تمكين أصحاب الشبكات وأي مشترك من سداد باقات ستارلينك عبر منصتنا، مع عمولة رمزية للمنصة، وتحكم إداري كامل، **بدون** أي ارتباط بالوكيل المحتكر.

## 2. الحقيقة التقنية (صريحة)

- لا توجد API عامة لسداد حسابات ستارلينك. الدفع يتم عبر بوابة الحساب نفسه (بطاقة) أو عبر Reseller API الحصري للوكلاء المعتمدين.
- النموذج الواقعي (نفس ما تعمله محلات «سداد ستارلينك» في السوق): **خط طلبات سداد** — العميل يدفع لنا، وفريق العمليات يسدد على حسابه أو عبر حسابات المنصة، والمنصة تنظم الطلب والعمولة والتتبع والإشعارات.
- التصميم يترك منفذاً (`StarlinkFulfillmentProvider`) لأتمتة التنفيذ لاحقاً إن حصلنا يوماً على Reseller API — دون تغيير الواجهات.

## 3. التدفق المقترح

```
صاحب الشبكة/المشترك                لوحة المشرف (العمليات)          ستارلينك
      │                                  │                            │
  يختار الباقة (بالدولار)           طلب في طابور «سداد ستارلينك»   يسدد الفريق على
  يدخل بيانات حسابه                يسدد ببطاقة/حساب المنصة   ──►   بوابة العميل
  يدفع من المحفظة                  يرفق إثبات السداد                  أو حساباتنا
      │                                  │                            │
  إشعارات: قيد السداد→مدفوع→مفعّل ◄─ اعتماد بضغطة                 الباقة تتفعل
```

## 4. النموذج (جدولان — additive فقط)

### `starlink_packages` — كتالوج الباقات (إدارة من اللوحة)
- `name`, `description`
- `official_price_usd` (decimal) — السعر الرسمي بالدولار
- `commission_type` (enum: `fixed`|`percent`) + `commission_value`
- `is_active`, `sort_order`
- قيم أولية مقترحة: Residential / Roam / Local Priority / Business — تُحدَّث من اللوحة مع تغير الأسعار

### `starlink_orders` — طلبات السداد
- `user_id`, `package_id`
- `starlink_account` (إيميل/Account ID), `starlink_terminal` (اختياري)
- `price_usd`, `commission_usd`, `total_usd`
- `fx_rate` (لقطة سعر الصرف وقت الطلب), `charged_yer` (المخصوم فعلياً من المحفظة)
- `status` (enum: `pending`|`paid`|`activated`|`rejected`|`cancelled`)
- `receipt_path`, `admin_note`, `handled_by` (المشرف المعالج)
- timestamps + soft deletes

## 5. العمولات (تحكم كامل من اللوحة)

- لكل باقة: عمولة ثابتة أو نسبة %، مع إعداد عام افتراضي
- خصم المحفظة: `السعر الرسمي + العمولة` بالدولار × سعر الصرف (لقطة مسجلة)
- العمولة بند مستقل → تقرير إيرادات السداد
- إعداد عام `starlink.commission_default` في AppSetting

## 6. بيانات حساب العميل — خياران

1. **إيميل + Account/Terminal ID**: الفريق يسدد على بوابة حساب العميل (الأنظف — لا أسرار محفوظة)
2. **حسابات/أجهزة ملك المنصة**: العميل يستأجر خدمة على حسابنا ويدفع التجديد دورياً (نموذج «ستارلينك مشاركة» — أسهل تشغيلاً، صفر بيانات حساسة)

**ملاحظة**: لا تُخزَّن كلمات مرور ستارلينك للعملاء أبداً — مسؤولية أمنية.

## 7. نقاط التكامل (إعادة استخدام — صفر اختراع)

| المكوّن | يعيد استخدام |
|---|---|
| خصم المحفظة | `WalletService` الحالي (خصم + استرداد عند الرفض) |
| مراجعة الطلبات | نمط موافقة/رفض مدفوعات MikroTik/المحاسبة (typed closures!) |
| الإشعارات | `UserNotification` القائم (حالة → إشعار عربي) |
| سعر الصرف | `ExchangeRateSetting::current()` أو إعداد مخصص |
| اللوحة | موردا Filament جديدان (باقات + طلبات) بمجموعة «الخدمات» |
| التطبيق | شاشة «سداد ستارلينك» — كتالوج، نموذج طلب، تتبع حالة |

## 8. ضمانات عدم الكسر

- جدولان جديدان فقط، لا تعديل أي جدول/عمود قائم
- كنترولر API مستقل تحت `/network-owner/starlink/*` أو مسار خدمات مستقل
- لا تعديل على topup/wallet/subscriptions/CyberNet/المحاسبة
- كل closures في الموارد الجديدة typed بـ `$record`/`$state` منذ اليوم الأول
- ميزة اختيارية — لا اشتراك يقيدها إلا إن قرر المشرف ربطها بمفتاح entitlement لاحقاً
